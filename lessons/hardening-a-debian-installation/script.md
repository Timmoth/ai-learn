Welcome. In this lesson we are going to walk through hardening a fresh Debian server. A clean Debian installation is, by reputation, a remarkably sensible default. A small base system, sane permissions, no listening services beyond SSH, and a release cadence that values being boring above all else. But it is not, out of the box, hardened. The defaults are tuned for compatibility and convenience. Root can be reached over SSH with a key. The firewall is not enabled. Kernel knobs are set for maximum interoperability. And there is nothing watching the authentication log for brute-force attempts.

Hardening, in this context, is the process of reducing what your server exposes to the network, and reacting faster when something does try to abuse it. It is not a checkbox you tick once. It is a small handful of layered habits, each of which is cheap on its own. We will work through six of those layers, in roughly the order you would apply them to a new machine: user accounts and sudo, SSH, the firewall, fail2ban for intrusion prevention, automatic security updates, and kernel sysctl tuning.

A quick note on scope. This is the baseline you would apply to a public-facing Linux box that runs a couple of services. It is not a hardened bastion build. It is not a CIS-compliant build. The goal is to push attack surface down by an order of magnitude with maybe an evening's work.

Before we get into the layers, let's pin down the threat model in one sentence. Most attacks against a public Linux server are not bespoke. They are commodity. SSH credential stuffing from a botnet. Exploitation of an unpatched service whose CVE was published yesterday. Password reuse from a breached dump. Kernel exploits aimed at a service running as root. The defences in this lesson are aimed at exactly that population of attacks. Sophisticated, targeted attackers are a different problem, and they are not what we are solving here.

Let's start with layer one, user accounts and sudo. The very first thing to fix is that you should not be logging in as root. Root SSH access is the single most attractive credential on any Linux box. So the first move is to create a regular admin user with adduser, add them to the sudo group with usermod, and from that point on, use sudo to escalate when needed. Debian uses the sudo group, not the wheel group. That is the historical difference between the Debian family and the Red Hat family. Membership of the sudo group is what /etc/sudoers recognises by default on Debian.

A few sudo policies are worth getting right early. Always edit /etc/sudoers using visudo. It validates the syntax before saving, and a bad sudoers file can lock you out of sudo entirely. Always require a password. NOPASSWD is convenient on CI runners, but it removes the authentication checkpoint that catches an attacker who has gained a shell but does not know your password. If a script genuinely needs to run one specific command without a password, scope the NOPASSWD entry to that one command, not to the whole user. And periodically audit who is actually in the sudo group. People leave teams, and their privileges should leave with them.

While you are here, lock the root password using `passwd -l root`. You can still get a root shell via `sudo -i`, because sudo does not care about root's password. Locking it just removes a credential that nobody should be using.

A separate concern is password quality for the human accounts that remain. Debian ships with libpam-pwquality, which lets you set minimum length, character class requirements, and dictionary checks via /etc/security/pwquality.conf. For a server where the only password is a sudo password, requiring twelve characters with at least one of each class is reasonable. For a server where humans never type a password at all — pure key-only SSH — it matters less.

Layer two is SSH hardening. SSH is the front door, and on most servers it is the only service exposed to the internet. The threats are well understood. Credential brute-forcing, weak ciphers, and the occasional vulnerability in sshd itself. The defences are correspondingly well understood, and they fall into three groups.

First, switch to key-based authentication. Generate an Ed25519 keypair on your workstation, not on the server, using `ssh-keygen -t ed25519`. Ed25519 is the right default in 2026. It produces a small private key, a public key that fits on one line, and it is faster than RSA for the same security level. The only reason to use RSA today is to talk to a system running OpenSSH older than 6.5, which is rare on anything you would call a server. Then copy the public key to the server with `ssh-copy-id`, which places it in your authorized_keys file with the right permissions. Test that you can log in with the key before disabling password authentication.

Second, edit the sshd configuration. On modern Debian, the main file at /etc/ssh/sshd_config typically ends with an Include directive that pulls in everything under /etc/ssh/sshd_config.d, so dropping your hardened settings into a new file under that directory is usually neater than editing the main file. The settings that matter are a small list. Set PermitRootLogin to no. That is stricter than Debian's default of prohibit-password, and it is the right choice once your sudo user works. Set PasswordAuthentication to no. This is the single highest-impact change on the whole list, because it removes the entire population of credential-stuffing attacks. There is no password to stuff. Set ChallengeResponseAuthentication and KbdInteractiveAuthentication to no, so that nothing else can sneak password-shaped auth back in. Add an AllowUsers line listing exactly the user accounts that may even attempt to log in. This is a positive allowlist, so even if a future package adds a system user, that user cannot SSH in unless you explicitly add them. Set MaxAuthTries to about three — enough for a typo, not enough for a brute-force — and combine it with a short LoginGraceTime of around thirty seconds, so each connection has a noticeable cost. Set ClientAliveInterval to about three hundred and ClientAliveCountMax to two, which drops idle or half-dead sessions cleanly. And turn off the features you do not use: X11Forwarding, AllowTcpForwarding, PermitUserEnvironment, and PermitEmptyPasswords, all set to no.

Third, and this is the load-bearing part, test before you commit. The number-one hardening mistake on a remote server is locking yourself out. Always run `sudo sshd -t` to validate the syntax of your configuration. No output means it parses cleanly. Keep your current SSH session open. In a second terminal, reload SSH with `systemctl reload ssh`, and then attempt a fresh login. If anything is wrong, the original session lets you fix it. Only close the original session after you have verified that a brand-new login works.

A quick side note on cipher hygiene. Modern OpenSSH defaults are already good. If you want belt-and-braces, you can pin the algorithms to the modern set: Curve25519 for key exchange, Ed25519 for host keys, ChaCha20-Poly1305 and AES-256-GCM for symmetric encryption, and the encrypt-then-MAC variants of SHA-256 and SHA-512 for message authentication. A small Python tool called ssh-audit can tell you exactly what your sshd is currently advertising and where the weak spots are.

And one more side note on changing the SSH port. Moving SSH off port 22 is folklore advice. It does cut a lot of noise out of your authentication log, because the loudest scanners only hit port 22. But it is not a security feature. A real scanner finds the new port in seconds. Treat it as log hygiene, not as defence. And if you do change it, remember to update your firewall rule and your fail2ban jail to match.

Layer three is the firewall. On a fresh Debian, the kernel's netfilter framework is sitting there doing nothing useful, because no rules are loaded. The job of a firewall on a server is to enforce default deny on inbound traffic. Explicitly allow the ports your services need, and drop everything else. On Debian, the easiest way to do that is UFW, which stands for Uncomplicated Firewall.

UFW is a thin frontend over the kernel's packet filter. On Debian 12, the backend is iptables. On Debian 13 and on modern distributions in general, it has shifted to nftables. From the user's perspective UFW behaves the same. The commands you type produce rules that the kernel enforces. UFW is not the only option. nftables directly is more powerful and is the modern Linux standard. firewalld is more common on Red Hat-family distributions. But for a single Debian server, UFW's terseness is its main selling point. It is hard to write a confused UFW rule.

The fundamental gotcha with any firewall configuration over SSH is the same as the SSH gotcha. You can lock yourself out. The cure is to allow SSH first, then enable the firewall. So you `apt install ufw`. You set the default policy to deny incoming and allow outgoing. You explicitly allow SSH on whatever port you use — and here is a useful trick. Use `ufw limit`, not `ufw allow`, on the SSH port. The limit verb allows the connection but rate-limits a source IP to roughly six attempts in thirty seconds, dropping anything past that. That gives you a free rate-limiter that stacks well with fail2ban. Then you allow whatever application ports your server actually serves — port 80 for HTTP, port 443 for HTTPS, and so on. Only after those rules are in place do you run `ufw enable`.

The command `ufw status verbose` shows the current ruleset. The variant `ufw status numbered` is what you want when you need to delete a specific rule by its index.

One more thing on the firewall: IPv6. If your server has IPv6, and most modern hosting does, confirm that /etc/default/ufw contains the line IPv6 equals yes. UFW will then apply equivalent rules to both stacks, which is what you want. Otherwise, you can end up with a tightly closed IPv4 perimeter and a completely wide-open IPv6 one. This is one of the more common ways a so-called hardened server is silently exposed.

When should you drop down from UFW to nftables directly? UFW is fine for a single-purpose server. If you need stateful matching beyond simple port rules, things like geo-blocking, complex NAT, or per-service rate limiting at the packet level, you should reach for nftables. The configuration lives in /etc/nftables.conf, and it is a much more expressive language. UFW is the right starting point. It is not the only stop.

Layer four is fail2ban. Fail2ban is a daemon that does one thing. It tails log files, and when it sees a pattern that matches "this IP just failed authentication N times", it adds a firewall rule that blocks the IP for a while. Conceptually it is trivial. Operationally it is remarkably effective against the commodity brute-force traffic that is the single largest source of noise in any public Linux server's authentication log.

The vocabulary is a little jargon-heavy but small. A filter is a regular expression, with a small amount of helper logic, that knows what a failed-authentication line looks like for a particular service. Debian ships filters for sshd, postfix, dovecot, apache-auth, nginx-limit-req, and dozens of others, all under /etc/fail2ban/filter.d. An action is what to do when the filter trips. By default, it adds an iptables or nftables rule that drops packets from the offending IP. Other actions exist — send an email, call a webhook, write to an ipset — but the firewall-drop action is the workhorse. And a jail ties a filter to an action and adds the thresholds. Which log to watch, how many failures within how much time count as a ban, and how long the ban lasts.

The configuration thing not to do is edit jail.conf directly, because it is overwritten on package upgrade. Drop your overrides in /etc/fail2ban/jail.local. A reasonable starting point sets ignoreip to your local networks and loopback, a findtime of ten minutes, a maxretry of five, and a bantime of one hour. There is also a useful option called bantime.increment, which exponentially increases the ban duration for repeat offenders. A first offence gets the configured bantime, a second offence gets double, a third gets quadruple, and so on. The cumulative effect on a determined botnet is significant.

For the sshd jail itself, two settings are worth being explicit about. Set the port to ssh, or to whatever port you actually use. And set the backend to systemd. That tells fail2ban to read the systemd journal directly rather than tail the legacy /var/log/auth.log file. On modern Debian, the journal is the more reliable source, because auth.log may not exist if you do not have rsyslog installed.

After editing, validate the configuration with `fail2ban-client -t`, then reload the service. You can inspect a jail's state with `fail2ban-client status sshd`, which shows currently-banned IPs and recent activity. And if you fat-finger yourself into a ban, `fail2ban-client set sshd unbanip` lets you undo it.

One honest assessment. Fail2ban is not a substitute for key-based authentication, and the project's own readme says so. If passwords are off, the brute-forcers cannot succeed anyway, and fail2ban's main contribution becomes keeping your log volume manageable and absorbing some of the connection cost. Run both. Key-only auth is the actual defence. Fail2ban is the cleanup crew.

Layer five is automatic security updates. The most common way a hardened server gets compromised is not a clever attack. It is a published CVE in a service the server runs, and an admin who was meaning to apply the update next week. Automatic security patching closes that window.

Debian's tool for this is unattended-upgrades, and on recent Debian releases it is installed by default, just not always enabled. The job has three parts. Confirm it is installed. Tell it to actually run. Tell it which origins of packages it is allowed to install updates from.

You install it with `apt install unattended-upgrades apt-listchanges`, and then run `dpkg-reconfigure --priority=low unattended-upgrades`. That writes a small file called 20auto-upgrades into /etc/apt/apt.conf.d, which contains the two switches that decide whether anything happens at all. One enables periodic update of the package lists. The other enables the unattended upgrade itself.

The actual policy — which upgrades to install — lives in /etc/apt/apt.conf.d/50unattended-upgrades. On Debian Bookworm and Trixie, the default Origins-Pattern includes the security suite and not much else, which is the sane default. You can enable stable point releases by uncommenting the relevant line, if you want patch-level releases of stable packages to flow automatically.

A few other options in that file are worth setting deliberately. Turn on Remove-Unused-Kernel-Packages so old kernels do not accumulate. Turn on Remove-New-Unused-Dependencies for the same kind of reason. Configure mail notifications by setting the Mail option to root or to a real address. And then the contentious one: Automatic-Reboot. A kernel update is not really applied until the system reboots. If you never reboot, you are running with a vulnerable kernel even though the package on disk is current. For a single-purpose server that can tolerate a brief outage at three in the morning, automatic reboots are the right default, with the reboot time set to something like 03:00 and Automatic-Reboot-WithUsers set to false. For a database primary or anything stateful, you probably want manual reboots and a monitoring rule that nags you when the file /var/run/reboot-required exists.

On modern Debian, the scheduler is a pair of systemd timers, apt-daily.timer and apt-daily-upgrade.timer. You can see when they will next fire with `systemctl list-timers` and a filter for apt-daily. And you can do a dry run to see what unattended-upgrades would install right now by passing the dry-run and debug flags. That is worth running once after the initial setup, just to confirm everything is wired up.

Layer six is kernel and sysctl hardening. sysctl is the interface to runtime kernel parameters, most of which can be set persistently in /etc/sysctl.conf, or more idiomatically on modern Debian, in a file under /etc/sysctl.d. The kernel exposes thousands of parameters. A small subset of them have direct security implications. The goal of sysctl hardening is to flip off a number of legacy networking behaviours that an attacker can use to spoof traffic, redirect routes, or probe for information about the kernel.

The settings fall into four rough categories. The first is anti-spoofing and source-routing. Reverse path filtering, set with rp_filter to one, makes the kernel reject packets whose source address does not match the route they came in on. That stops most IP spoofing. Disabling accept_source_route stops attackers from supplying their own routing instructions inside the packet, on both IPv4 and IPv6. Disabling accept_redirects and send_redirects stops the kernel from trusting ICMP redirect messages, which is correct because your server is almost certainly not a router. Enabling log_martians records anything that arrives claiming an unroutable source address.

The second category is denial-of-service resistance. tcp_syncookies, set to one, makes the kernel cookie its way out of an exhausted SYN backlog under a flood. icmp_echo_ignore_broadcasts, set to one, stops the server from participating in classic Smurf amplification attacks. icmp_ignore_bogus_error_responses cleans up some attacker-crafted error packets.

The third category is address-space and information-leak protection inside the kernel. randomize_va_space, set to two, enables full address space layout randomisation. kptr_restrict, set to two, hides kernel pointers from anything that reads /proc. dmesg_restrict, set to one, stops unprivileged users from reading the kernel ring buffer, which can leak information after a crash. And ptrace_scope, under the kernel.yama namespace, restricts ptrace to direct parent processes, which limits the damage a compromised user account can do to other processes.

The fourth category is filesystem race protection. protected_symlinks, protected_hardlinks, protected_fifos, and protected_regular all close off well-known time-of-check to time-of-use race conditions that exploit how unprivileged users can interact with privileged programs through shared directories like /tmp. The suid_dumpable knob, set to zero, prevents setuid binaries from writing core dumps that would otherwise contain privileged memory.

You drop these into a file like /etc/sysctl.d/99-hardening.conf, and apply them without rebooting by running `sudo sysctl --system`. That re-reads everything under /etc/sysctl.d, /run/sysctl.d, and /etc/sysctl.conf.

One note on cargo culting. Every one of those settings has a reason, but some of them have been the Debian default for years. randomize_va_space at two is already on. Setting it explicitly is harmless, and it makes the intent legible to the next admin who reads your config, which is the main argument for being explicit. Other settings have real trade-offs. kernel.modules_disabled set to one prevents you from loading any kernel module after boot. That is a clean security win, and it also means you cannot debug an issue by loading something like nf_conntrack_ftp from a recovery shell. Choose what fits your operational model.

Let's wrap up with what this baseline does not cover, because that is just as important. AppArmor ships and is enabled on Debian, so you have a basic mandatory access control layer for free, but writing custom profiles for the specific services you run is a separate exercise. Centralised log shipping is essential if you actually want to notice an attack rather than just deter one. journald-remote, rsyslog, or a more ambitious tool like Loki or Elastic all play that role. File integrity monitoring with AIDE or Tripwire, and intrusion detection with auditd, OSSEC, or Wazuh, all sit above this baseline. Two-factor authentication on SSH, via pam_google_authenticator or via a hardware token using pam_u2f, is the obvious next step after key-only auth.

The point of the baseline we have built here is that it gets you eighty percent of the way for an evening's work. The remaining twenty percent are not less important. They are just bigger projects with their own learning curves.

To close, here is a reasonable order of operations on a brand-new Debian VM. Update everything with `apt update` followed by `apt full-upgrade`. Create your sudo user, lock the root password, and get key-based SSH working as the sudo user. Edit your sshd config, validate it with `sshd -t`, reload, and confirm a fresh login still works. Install and configure UFW with default-deny and an explicit allowlist for SSH and your service ports. Install fail2ban with a sane jail.local. Install and enable unattended-upgrades, and do a dry-run to confirm. Drop your sysctl hardening file at /etc/sysctl.d/99-hardening.conf and apply it. And finally, reboot once, to prove that the box still comes up correctly with every change in place.

That last point is the only one that requires courage. A configuration that works until the next reboot is a footgun waiting for the next power event. Cycle the box once while you are still paying attention. Thanks for listening.
