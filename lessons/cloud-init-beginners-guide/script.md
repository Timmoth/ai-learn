Welcome. In this lesson, we are going to build a clear mental model of cloud-init. When you launch a virtual machine on AWS, Azure, GCP, DigitalOcean, OpenStack, or really any modern cloud, something has to turn that generic base image into your specific instance. Something sets the hostname, installs your SSH key, creates your user, applies your packages, and runs your first-boot scripts. On almost every Linux cloud image in production today, that something is cloud-init. By the end of this lesson, you will know what cloud-init is, the stages it runs through at boot, the datasources it reads, the cloud-config YAML you write, and how to test all of that on your own laptop before you ever pay for a cloud instance.

Let's start with what cloud-init actually is. Cloud-init is an open source program that initializes a cloud instance the first time it boots. The idea is simple, and it solves a very practical problem. Cloud providers want to ship one generic image: one golden Ubuntu, one golden RHEL, one golden Amazon Linux, and have every customer's instance customize itself the very first time it powers on. Cloud-init is the standard mechanism for doing that customization in a way that works across providers. It is pre-installed on the official cloud images for Ubuntu, Debian, Fedora, RHEL, CentOS Stream, Rocky, AlmaLinux, openSUSE, FreeBSD, and many others. It supports more than thirty datasources, including Amazon EC2, Microsoft Azure, Google Compute Engine, Oracle Cloud, OpenStack, DigitalOcean, VMware, LXD, and a special local datasource called NoCloud that you will hear more about later. It works equally well on cloud virtual machines, on-premises hypervisors, and bare metal servers.

The problem cloud-init solves is mundane but everywhere. Configuring a fresh instance is complex and error-prone, and doing it the same way across many clouds, many distributions, and many instance counts is much worse. Cloud-init turns that task into a single YAML file.

Now let's talk about how cloud-init works at a high level. Cloud-init is driven by three kinds of input. The first is meta-data. Meta-data is the set of facts about the instance, provided by the cloud platform itself. It includes things like the instance ID, the hostname, the region, the availability zone, and the network configuration. You do not write this. The platform does. The second input is user-data. User-data is what you, as the user, hand to the cloud at launch time, telling cloud-init what to do. In the vast majority of cases, this is a cloud-config YAML document. The third input is vendor-data. Vendor-data is optional extra configuration that the cloud provider may inject for you, for example to install that provider's command-line tool. Cloud-init pulls all three of these from something called a datasource, merges them into a single plan, and then executes that plan in a series of stages.

Let's walk through those stages, because understanding the order is essential when you are debugging. Cloud-init runs in five sequential stages, and each one is implemented by a systemd unit.

The first stage is detection. Before cloud-init really starts, a small shell tool called ds-identify inspects the running system. It looks at DMI strings, the kernel command line, and any available block devices to figure out which cloud the instance is running on. The result decides whether cloud-init runs at all and which datasource it should use.

The second stage is the local stage, implemented by the cloud-init-local service. This runs as soon as the root filesystem is mounted read-write, before networking comes up. Its job is to find a local datasource, like a configuration drive, a NoCloud seed disk, or kernel command-line arguments, and to apply network configuration. This stage actually blocks network bring-up, so that the network can be configured correctly the very first time.

The third stage is the network stage, implemented by the cloud-init-network service. This runs once networking is online, and it is the heavy stage. Cloud-init reaches out to any remote metadata service, fetches the user-data, decompresses or decodes it, processes any include directives or MIME parts, and then runs the early modules, including disk setup, filesystem creation, mount configuration, and the bootcmd module. SSH and console login are blocked until this stage finishes.

The fourth stage is the config stage, implemented by the cloud-config service. This runs the bulk of the non-critical configuration modules. Things like setting the timezone, installing CA certificates, and configuring apt sources happen here. This stage does not block the rest of boot.

The fifth and final stage is, fittingly, called final, implemented by the cloud-final service. This is the rc.local of cloud-init. It installs packages, runs your custom runcmd commands, hands off to a real configuration management system like Chef, Puppet, or Ansible-pull if you have asked it to, and emits a final status. If you have other scripts that need to wait for cloud-init to finish, they can do so by running cloud-init status with the wait flag.

The key intuition here is that networking-sensitive work goes early, in the local and network stages. Most of your YAML directives run in the config or final stage. And your custom shell commands almost always run at the very end.

Now let's talk about datasources and environment detection. A datasource is cloud-init's name for the way that a particular cloud hands cloud-init its data. Each supported cloud has its own datasource module that knows the right URL to hit, the right disk to look at, or the right kernel argument to read. A few examples. The EC2 datasource fetches data from a special link-local HTTP endpoint, at the well-known address 169.254.169.254. The Azure datasource combines a small ovf-env.xml file on an attached CD-ROM with the Azure Instance Metadata Service. The GCE datasource reads metadata from an internal hostname called metadata.google.internal. The ConfigDrive datasource reads from a small attached ISO formatted by the OpenStack provider. And the NoCloud datasource reads user-data and meta-data from a local filesystem labelled cidata, with no network involved at all. NoCloud is the datasource you will use for local testing.

Detection is almost always automatic. The ds-identify tool figures it out for you. You only need to intervene if you are running cloud-init somewhere unusual, in which case you can pin the datasource list by dropping a small configuration file into the cloud-init configuration directory under /etc/cloud/cloud.cfg.d, listing only the datasources you want cloud-init to try.

Now the most important part: writing cloud-config user-data. User-data can take several formats, but the most common one, and the one you will spend almost all of your time on, is cloud-config. Cloud-config is a YAML document whose very first line is the literal comment hash cloud-config. That magic header is how cloud-init recognizes the format. Without it, your YAML will be silently ignored. Other supported formats include plain shell scripts, with the usual shebang line; include files; gzip-compressed payloads; MIME multipart archives; and Jinja-templated documents. But cloud-config is what you will write most of the time.

Let's walk through what a realistic cloud-config document looks like. At the top, you have your identity settings. You set the hostname to something like web-01. You set the fully qualified domain name to web-01.example.com. You set the timezone to Europe/London. Next, you usually create a user. You give the user a name, like deploy, a description, a group like sudo, a shell like bash, and a sudoers rule that lets the user run anything as root without a password. You typically set lock_passwd to true, so the user can only log in via a key. And you provide one or more public SSH keys under ssh_authorized_keys. After that, you usually want package management. You set package_update to true to refresh the package index, package_upgrade to true to upgrade everything that has an update, and then you list the packages you want, like nginx, git, and curl, under the packages key. Next, you might use the write_files module to drop one or more configuration files into place. For each file, you specify a path, an owner, a permissions string like 0644, and the content of the file inline. For example, you might write a small nginx server block that listens on port 80 and serves files from /var/www/html. Finally, at the bottom, you use the runcmd module to list shell commands that cloud-init should run at the very end of boot. For example, you might symlink your nginx site configuration into the enabled directory, restart nginx, and write a small greeting to the web root.

A few details that catch beginners out, and that are worth saying explicitly. First, the hash cloud-config line is not optional, and it is not a comment in the YAML sense. Cloud-init parses it as a format marker. If you forget it, the rest of the file does nothing. Second, runcmd runs in the final stage. If you need something earlier, use bootcmd, which runs on every boot, in the network stage. Third, if you define a users list, it replaces the default user list. If you want to keep the cloud image's default user, like the ubuntu user, and just add one of your own, include the special value default as the first entry in the users list. And fourth, cloud-config is processed once per instance ID, not once per boot. Re-running it requires either a new instance ID, or running cloud-init clean and then rebooting.

Cloud-config covers far more ground than we have time for. A non-exhaustive tour: there are modules to configure apt and yum repositories, to manage SSH keys and host keys, to partition disks and create filesystems and write fstab entries, to install trusted CA certificates, to reboot or power off when cloud-init finishes, and to hand off to a real configuration management system like Chef, Puppet, or Ansible once the box is reachable. Every module has a JSON schema, and the cloud-init schema command with the system flag will validate your real user-data against it.

Finally, let's talk about testing and debugging cloud-init locally. You do not need a cloud account to learn cloud-init. The NoCloud datasource exists precisely so you can hand cloud-init a user-data file and a meta-data file from a local disk image, and watch it run inside a virtual machine on your laptop. The fastest path on a laptop is the cloud-localds helper on Debian or Ubuntu, or the cloud-init snap, together with QEMU. The recipe is short. First, you write a minimal meta-data file containing an instance ID and a local hostname. The instance ID is what cloud-init uses to decide whether this is the first boot, so changing it forces cloud-init to run again. Second, you write your cloud-config user-data file, with the hash cloud-config header, your hostname, a user with an SSH key, and a runcmd that does something simple like writing a marker file to /tmp. Third, you use cloud-localds to bake those two files into a seed ISO, with the volume label cidata. And fourth, you boot an Ubuntu cloud image in QEMU, attaching the seed ISO as a second drive and forwarding a port for SSH access. Cloud-init will detect the seed ISO as a NoCloud datasource and run your configuration.

Once the virtual machine is up, there are four commands that cover almost all debugging. The first is cloud-init status with the long flag. This tells you whether cloud-init has finished, and which datasource it picked. The second is cloud-init schema with the system and annotate flags, which validates the user-data that the instance actually received and prints inline error annotations. The third is cloud-init query userdata, which prints the user-data that cloud-init saw, after any decoding. The fourth is cloud-init clean with the logs flag, which wipes all cloud-init state so that the next boot behaves like a first boot. That last one is essential when you are iterating.

Two log files are worth bookmarking on every cloud-init system you touch. The first is cloud-init.log, under /var/log. This is cloud-init's own structured log of everything it did, broken down by stage and by module. Most of your "why didn't my module run" questions are answered here. The second is cloud-init-output.log, also under /var/log. This file captures the standard output and standard error from runcmd, bootcmd, and package installations. When your shell snippet misbehaves, this is where you will find the error message.

For an even faster feedback loop, modern Linux distributions support tools like Multipass, which is Ubuntu's lightweight virtual machine tool, and LXD, which is a system container manager. Both of them let you launch a fresh instance with your cloud-config in under ten seconds, without ever touching QEMU directly.

Let's put it all together one more time. The full mental model fits in a single paragraph. A cloud-init-enabled image boots. The ds-identify tool decides which datasource to use. Cloud-init runs through the local, network, config, and final stages, pulling meta-data, user-data, and vendor-data from that datasource. Your contribution is a hash cloud-config YAML document that lists users, packages, files, and commands. Cloud-init's modules apply that document at the right stage. Locally, you can reproduce the whole thing with a seed ISO and a cloud image. And you debug it with cloud-init status, cloud-init schema, and the two log files under /var/log.

From here, the natural next step is to write a one-page cloud-config that creates your user, installs your favourite packages, and prints a banner, and then to launch it twice. Once locally, using NoCloud, and once on whatever cloud you actually use. When the same YAML works in both places, you have learned cloud-init. Thanks for listening.
