.NET 11 is the next annual release of the platform. It is currently in preview, and is scheduled to ship in November 2026. As a Standard Term Support release, it succeeds the long term support release of .NET 10, and most of its surface area is already stable enough to try out in real projects.

In this lesson we will tour what is actually changing. We will look at the C# 15 language additions, the runtime and JIT work, the ASP.NET Core updates, the BCL APIs you will reach for in day to day code, and the things you need to know before you bump a target framework from net10.0 to net11.0. The lesson assumes you are comfortable with C# and have written or maintained a .NET application before.

To start using it, you install the .NET 11 preview SDK and change your project's target framework to net11.0. If you want to opt into the C# 15 features, you also set the LangVersion property to preview. One thing to note is that you no longer need to set EnablePreviewFeatures to true for runtime async on net11.0. That requirement was relaxed for this release. Other preview features, such as the discriminated union scaffolding types, still require it.

Let's start with the C# 15 language features. C# 15 ships with .NET 11. The headline additions are small but expressive.

The first one is union types. C# finally gets first class unions. A union represents a value that can be one of several known case types. You declare a union using the new union keyword. So for example, you might have three record classes, Cat, Dog, and Bird, and then declare a single union called Pet, whose case types are exactly those three record classes.

The compiler provides implicit conversions from each case type into the union, and it makes switch exhaustiveness a hard guarantee. So when you write a switch expression on a Pet, you must include an arm for Cat, an arm for Dog, and an arm for Bird. If you forget a case, the compiler tells you at compile time, instead of you finding out at runtime when the unhandled case throws an InvalidOperationException. The runtime side of this feature is exposed in System.Runtime.CompilerServices as the types UnionAttribute and IUnion. Libraries can author against the surface today, although some features from the original proposal, in particular union member providers, are still being filled in across previews.

This is the feature that people coming from F#, Rust, Swift, or TypeScript have been asking about for years. It replaces a pile of OneOf-style NuGet packages and ad hoc inheritance hierarchies with one supported pattern.

The second C# 15 feature is collection expression arguments. Collection expressions in C# 12 gave you bracket syntax for collections, with spreads. C# 15 lets you pass arguments to the underlying collection's constructor by using a with element at the head of the expression. For example, you can create a List of string and tell it to preallocate its capacity to twice the length of a source array, by putting a with capacity argument as the first element of the collection expression. Or you can create a HashSet of string and pass StringComparer.OrdinalIgnoreCase as the comparer, again using a with element at the head. Before C# 15, you had to fall back to constructing the HashSet manually with the comparer in the constructor, which is awkward inside expressions or init initialisers. The new syntax keeps the collection expression form for the common cases that previously fell off the cliff.

Now let's move to the runtime. The biggest engineering investment in .NET 11 is finishing the move from compiler generated async state machines to runtime native async. This feature is called runtime async, or Runtime Async V2. Instead of the C# compiler emitting a state machine class for each async method, the runtime itself tracks suspension and resumption.

You opt in per project by adding a Features property with the value runtime-async equals on, in your csproj file. Note that the .NET 11 runtime libraries themselves are already compiled with runtime async turned on, so even apps that don't enable it pick up the change indirectly when they call into the BCL. ASP.NET Core's shared framework libraries are also compiled with it on net11.0 and later.

What do you get from this? The most visible effect is cleaner live stack traces. If you walk a chain of three awaits today, and then capture a new StackTrace, you see roughly thirteen frames threaded through the AsyncMethodBuilderCore.Start internal method. With runtime async, you see only the five frames that actually exist in your code. Profilers, debugger call stack windows, and any logging that captures live stacks all benefit. Exception stack traces already looked clean, because ExceptionDispatchInfo had been papering over the compiler generated frames.

You also get lower overhead. The runtime reuses continuation objects more aggressively, and it skips saving locals that did not change across an await, so allocation pressure in async heavy code drops. You get better debugging, because breakpoints inside runtime async methods bind correctly, and stepping through await does not bounce you into compiler generated infrastructure. And you get broader codegen, because runtime async now works under NativeAOT and ReadyToRun, including inlining of awaitless async calls, which is the synchronous fast path.

A couple of things to know about it. To opt out per project, you use the UseRuntimeAsync property set to false in your csproj. The older DOTNET_RuntimeAsync and UNSUPPORTED_RuntimeAsync environment variables have been removed. And because runtime async changes codegen for a large portion of the framework, you should test your apps against the preview and watch for regressions around ExecutionContext and AsyncLocal flow, and around exception propagation.

Now let's talk about JIT and codegen improvements. The JIT picks up several optimisations that mostly show up after inlining, where guards from different methods land in the same compiled body.

The first is constant folding of SequenceEqual and string.Equals. When both operands are compile time constants, that includes string literals, const string fields, and UTF-8 literals like the bytes for PNG with the u8 suffix, the JIT replaces the comparison with the constant true or false result. So if you have a helper method that compares a role to the string Admin, and a caller passes the literal Guest, the JIT sees Guest equals Admin and folds the call to false at compile time, after inlining.

The second is better bounds check elimination. The pattern where you compare i plus a constant against a length now elides the bounds check on the indexed access. Index from end access, like values bracket caret one bracket, has more redundant checks removed. And the JIT now picks up the implicit length not equal to zero assertion from a span.IsEmpty guard, so the bounds check on span bracket zero bracket inside the guarded branch is elided.

The third is redundant branch elimination. If an outer predicate is already implied by an inner branch, the JIT folds away the redundant outer test. Similarly, if you assign a value conditionally with a ternary, and then immediately test it, the JIT eliminates the test and routes each ternary branch directly to its target. Again, these become visible after inlining.

The fourth is switch expression folding. Patterns like x is zero or one or two or three or four collapse into branchless checks, instead of a chain of comparisons.

There are also new hardware intrinsics. New Arm SVE2 intrinsics land. Half to float and float to Half conversions on x64 with F16C now use dedicated vcvtph2ps and vcvtps2ph instructions. Vector dot product on AVX lowers to mul plus permute plus add, instead of vdpps, which is consistently faster. And the runtime now reports SVE AES, SVE SHA3, SVE SM4, SHA3, and SM4 as separate instruction sets.

ReadyToRun also improves. Default comparers, that is Comparer of T dot Default and EqualityComparer of T dot Default, are now specialised in ReadyToRun images, mirroring NativeAOT. Microsoft's benchmarks show up to twenty times improvement for collection operations that hit the default comparer. ReadyToRun can also devirtualise non shared generic virtual calls.

Cached interface dispatch on non JIT platforms, primarily iOS, yields up to two hundred times improvements in interface heavy code, because what used to fall back to an expensive generic fixup path now uses the cached path. And Guid.NewGuid on Linux now uses the getrandom syscall with batch caching, instead of reading from slash dev slash urandom, which is about twelve percent faster.

Moving on to ASP.NET Core. There is a lot here, so we will work through it by area.

First, Kestrel and the request pipeline. Kestrel's HTTP/1.1 parser now uses a non throwing code path for malformed requests, returning a result struct instead of throwing BadHttpRequestException on every parse failure. In hostile traffic, things like port scanning or misconfigured clients, throughput improves twenty to forty percent. Valid request processing is unaffected. Kestrel also starts processing HTTP/3 requests without waiting for the control stream and SETTINGS frame, reducing first request latency on new connections.

Two TLS observability changes make handshake failures debuggable. The ITlsHandshakeFeature now exposes an Exception property containing the underlying exception from a failed handshake, instead of surfacing a bare IOException higher up. And the old TlsClientHelloBytesCallback option is now obsolete. You configure ClientHello inspection via the new ListenOptions.UseTlsClientHelloListener connection middleware instead.

Next, Zstandard compression, which is on by default. ASP.NET Core picks up Zstandard for both response compression and request decompression, and zstd is enabled by default alongside Brotli and gzip. Browsers that advertise zstd in their Accept-Encoding header now get Zstandard compressed responses out of the box. You can configure the Zstandard quality between one and twenty two via the ZstandardCompressionProviderOptions. The response compression middleware now also adds a Vary header with the value Accept-Encoding to every response when compression is enabled, even if the response itself isn't compressed. This is important for CDNs and shared caches that key on encoding.

Next, native OpenTelemetry tracing. ASP.NET Core now emits OpenTelemetry semantic convention attributes on the HTTP server activity directly. You no longer need a separate OpenTelemetry.Instrumentation.AspNetCore package. You just subscribe to the Microsoft.AspNetCore activity source in your OpenTelemetry configuration, and attributes like http.request.method, url.path, http.response.status_code, and server.address are populated automatically. If you don't want these attributes, you can suppress them via the Microsoft.AspNetCore.Hosting.SuppressActivityOpenTelemetryData AppContext switch.

Next, Minimal APIs and OpenAPI. Endpoint filters now run even when parameter binding fails. The filter can inspect the response status code, see that it is four hundred, and substitute its own response. In Development, you should set RouteHandlerOptions.ThrowOnBadRequest to false so the framework returns a 400 the filter can observe, instead of throwing into the developer exception page. Microsoft.AspNetCore.OpenApi updates to OpenAPI 3.2.0 via Microsoft.OpenApi 3.3.1, which is a breaking change in the underlying library. You opt in to the new version explicitly via the OpenApiVersion option. OpenAPI document generation now also recognises the HTTP QUERY verb as a known operation type, and emits FileStreamResult and FileContentResult types as binary string schemas instead of generic objects.

Now Blazor. Blazor gets a long list of improvements. Here are the ones most likely to affect existing apps.

Virtualisation no longer assumes equal item heights. The Virtualize component now adapts to measured item sizes at runtime, which fixes scrolling glitches in lists where items have different heights. The default OverscanCount rises from three to fifteen, to feed the average height calculation better. A new AnchorMode parameter, with values None, Beginning, and End, controls viewport pinning when items are dynamically added. Beginning is useful for a news feed style experience, where you want to stay pinned to the top. End is useful for chat or log views, where you want to stay pinned to the bottom.

TempData now works under static server side rendering. You can declare a CascadingParameter of type ITempData on your component, and use a SupplyParameterFromTempData attribute to persist data between HTTP requests during static SSR. This is good for flash messages, the post redirect get pattern, and one time notifications.

Relative navigation. NavigateTo and the NavLink component accept a RelativeToCurrentUri parameter set to true. With this, the target resolves against the current path, instead of the app's base URI. So if the browser is at slash docs slash getting started slash installation, navigating to configuration with the relative flag true takes you to slash docs slash getting started slash configuration, instead of just slash configuration at the app root.

Server triggered circuit pause. Server side Blazor can ask connected clients to begin the graceful pause flow via Circuit.RequestCircuitPauseAsync. This is useful for planned shutdowns, instance draining, and maintenance windows.

A BasePath component and a DisplayName component. BasePath renders the base href HTML tag automatically. DisplayName reads the Display Name attribute or the DisplayName attribute from model metadata.

And a new project template, blazorwebworker, scaffolds a Blazor WebAssembly app that runs CPU heavy work in a Web Worker, so the UI thread stays responsive.

For authentication and rate limiting. ASP.NET Core Identity migrates from DateTime and DateTimeOffset to TimeProvider, making lockouts, token expiration, and security stamp validation deterministic in tests via FakeTimeProvider. Passkey display names are inferred automatically from authenticator AAGUIDs for known providers, including Google Password Manager, iCloud Keychain, Windows Hello, 1Password, and Bitwarden. The FixedWindowRateLimiter now reports a RetryAfter value that reflects the next window boundary, so apps propagating that into the Retry-After header automatically produce accurate retry intervals.

Finally, the MCP server template. The mcpserver template, for building Model Context Protocol servers, now bundles with the .NET SDK rather than requiring a separate Microsoft.McpServer.ProjectTemplates install. You just run dotnet new mcpserver to scaffold one.

Now let's look at the BCL and API additions, starting with the biggest one. The Process API gets its biggest update in years. System.Diagnostics.Process finally gets the ergonomic helpers that most teams ended up writing themselves. You can do a one shot capture of standard output, standard error, and exit code, with a single call to Process.RunAndCaptureTextAsync. The new family includes Process.Run and RunAsync, Process.RunAndCaptureText and RunAndCaptureTextAsync, Process.ReadAllText, ReadAllBytes, and ReadAllLinesAsync, plus fire and forget options. Process.StartAndForget starts a child you don't intend to wait for. ProcessStartInfo.StartDetached detaches from the parent's session or console so the child outlives a terminal. And ProcessStartInfo.KillOnParentExit, on Windows only, terminates the child when the parent exits.

SafeProcessHandle gains Start, Kill, Signal, WaitForExit and WaitForExitAsync, and a ProcessId property. ProcessStartInfo also gains InheritedHandles, StandardInputHandle, StandardOutputHandle, and StandardErrorHandle properties, which let you control exactly which OS handles cross the fork boundary, instead of inheriting everything. Console output now honours the FORCE_COLOR standard, which is useful for piping coloured output through tee or into CI viewers.

For System.Text.Json. JsonNamingPolicy.PascalCase joins the existing camelCase, snake case, and kebab case policies. The JsonNamingPolicy attribute can be applied per member, to override the global policy without writing a custom converter. The JsonIgnore attribute is now valid at the type level. Apply it once at the top of a class or struct, and every member inherits the ignore condition. F# discriminated unions serialize out of the box, with no custom converter. Utf8JsonWriter.Reset accepts new writer options when repooling. And there is a strongly typed GetTypeInfo of T method on JsonSerializerOptions, which removes the manual downcast from the older non generic GetTypeInfo of Type.

For compression and archives. The System.IO.Compression namespace gains span based DeflateEncoder, ZLibEncoder, and GZipEncoder types that mirror the shape of BrotliEncoder. You can encode and decode without allocating a Stream. Zstandard joins the namespace as ZstandardStream and ZstandardEncoder. ZipArchiveEntry.Open with a FileAccess parameter, and a new CompressionMethod property, let you open entries for explicit read, write, or read write access, and inspect their compression. ZipArchive now validates CRC32 on read, so corrupt archives that previously passed silently now throw InvalidDataException. DeflateStream and GZipStream write format headers and footers even for empty payloads, which is a behaviour change if you depended on empty output. And TarFile.CreateFromDirectory accepts a TarEntryFormat parameter, so you can pick Pax, Ustar, GNU, or V7, instead of always producing Pax. TarReader now also handles the GNU sparse 1.0 PAX representation.

For strings, numerics, and low level I O. String gains Rune based overloads of Contains, StartsWith and EndsWith, IndexOf and LastIndexOf, Replace, Split, and the Trim family. Char.Equals with a StringComparison parameter brings ordinal versus culture aware comparisons to single characters. BitConverter adds BFloat16 round tripping for machine learning interop. The types double, float, and Half can format and parse in IEEE-754 hex form, which preserves every bit, for golden file tests and C printf percent a interop. A new RegexOptions.AnyNewLine flag makes the anchor characters and the dot wildcard treat all Unicode line terminators as newlines, not just backslash n. SafeFileHandle gets a Type property that reports whether a handle is a file, pipe, socket, or directory without P invoke, and a CreateAnonymousPipe method that makes an anonymous pipe pair with independent async settings. RandomAccess.Read and Write now work with non seekable handles like pipes. BitArray gets a PopCount method that returns the number of set bits efficiently. And Utf8.IndexOfInvalidSubsequence, along with Utf16.IsValid and IndexOfInvalidSubsequence, let parsers report the exact byte position of an encoding error, instead of bailing out with a generic exception.

For networking and TLS. HttpClient automatically downgrades to HTTP/1.1 when a request needs NTLM or Negotiate authentication, which HTTP/2 doesn't allow. Enterprise intranets using Windows auth no longer need explicit HttpRequestMessage Version overrides. On Linux, certificate validation failures now emit standard TLS alerts to the peer, instead of dropping the connection, matching Windows behaviour.

For caching observability. MemoryCache ships with built in OpenTelemetry compatible metrics, with no extra adapter package. You opt in by setting TrackStatistics to true on MemoryCacheOptions. The MemoryCache meter publishes four observable instruments. The cache requests instrument has a tag that distinguishes hit from miss. There is also a cache evictions instrument, a cache entries instrument, and an estimated size instrument. A new MemoryCache constructor takes an IMeterFactory for per instance metrics.

For the SDK and tooling. The dotnet watch command integrates with Aspire app hosts, recovers automatically after a crash, and supports device selection for MAUI and mobile. The dotnet run command gains a dash e option to pass environment variables from the command line. File based apps now support a hash colon include directive, so you can split a single file app across multiple files without scaffolding a project. The dotnet sln command can create and edit solution filter files. SDK installers on Linux and macOS are smaller, via assembly deduplication, and crossgen is skipped for tools only assemblies. OpenTelemetry replaces Application Insights for CLI telemetry. And there is foundation work for a NativeAOT dotnet CLI entry point.

Now let's talk about migration considerations, because the shift from .NET 10 to .NET 11 is mostly a recompile, but a few items need attention.

The change most likely to surprise you is the updated hardware baselines. .NET 11 raises the minimum CPU baseline. On x86 and x64, the baseline moves from x86-64-v1 to x86-64-v2, on all three operating systems. That requires CX16, POPCNT, SSE3, SSSE3, SSE4.1, and SSE4.2. In practice, anything Intel and AMD still officially support meets this. The chips that go below were last supported around 2013. But if you build container images for older bare metal fleets, or air gapped environments, validate before upgrading. Running .NET 11 on hardware below the baseline now fails with a startup message, saying the current CPU is missing one or more of the baseline instruction sets.

The ReadyToRun target also lifts to x86-64-v3 on Windows and Linux, which adds AVX, AVX2, BMI1, BMI2, F16C, FMA, LZCNT, and MOVBE. Hardware that meets the JIT baseline but not the R2R baseline will pay a small JIT cost at startup as the runtime falls back. On Arm64, Apple is unchanged. Linux is unchanged for the JIT and AOT minimum, but the ReadyToRun target adds LSE. And on Windows, the baseline updates to require LSE, and the ReadyToRun target updates to armv8.2 a plus RCPC.

Next, runtime async and async behaviour. Even if you don't enable runtime async in your own project, the BCL and ASP.NET Core's shared framework libraries are compiled with it. Most apps see only cleaner stack traces, but you should exercise your test suite, especially around ExecutionContext and AsyncLocal propagation, and around exception flow. The DOTNET_RuntimeAsync environment variable is gone. You use UseRuntimeAsync set to false in your csproj to opt out per project.

Next, empty Deflate and GZip output now writes headers and footers. If you rely on DeflateStream or GZipStream producing an empty file when no data is written, that changes in .NET 11. The streams now always emit format compliant headers and footers, which is what every other implementation already produces.

Next, OpenAPI 3.2 is a breaking dependency. If you use Microsoft.AspNetCore.OpenApi, the underlying Microsoft.OpenApi library jumps to 3.3.1 with breaking changes in the document model types. You should walk the Microsoft.OpenApi upgrade guide before bumping.

Next, ZIP CRC32 is now validated. Archives that previously passed without validation now throw InvalidDataException on a CRC mismatch. If your pipeline produced subtly corrupt ZIPs that nobody noticed, you will notice now. Which is the point.

And finally, preview versus stable surface. C# 15 features, that is unions and collection expression arguments, plus runtime async, are still labelled preview features in their respective designs, even though runtime async no longer requires EnablePreviewFeatures. Production projects should pin to released previews, and budget for at least one validation pass before adopting these specific features broadly. The library surface, the new Process API, the JSON improvements, the compression types, and the MemoryCache metrics, is stable.

To wrap up in one paragraph. .NET 11 is a polishing release with one large engineering bet, runtime async, and a lot of small wins everywhere else. The C# 15 additions, unions and collection expression arguments, tighten the language's modelling story. The JIT, ReadyToRun, and hardware intrinsics work shaves overhead from real workloads, without you changing code. ASP.NET Core picks up Zstandard, native OpenTelemetry, and a much better Blazor Virtualize. The BCL finally gets a sane Process API, and a stack of span based encoders. The things to watch when you upgrade are the hardware baseline lift, and the OpenAPI 3.2 breaking change. Everything else should just compile and run, faster and cleaner than before.
