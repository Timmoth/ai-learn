Welcome. In this lesson we are going to set up llama.cpp on a Linux machine to serve Qwen3.6 35B A3B locally, and we are going to wrap it in a systemd service so that the inference server starts on boot, restarts on failure, and logs to the journal. By the end you will have a private, OpenAI-compatible endpoint sitting on a port of your choosing, doing real work behind whatever client you point at it.

There is a moment in every local language model journey where the toy "Ollama run" command stops being enough. You want a real OpenAI-compatible endpoint on a stable port. You want it to come back after a reboot. You want to pick the model, pick the quantisation, pick the context window, and pick how the experts of a mixture-of-experts model are laid out across CPU and GPU. That is what llama.cpp was built for, and the version of llama-server shipping in 2026 has finally caught up to a point where running a 35 billion parameter mixture-of-experts model on a single workstation is genuinely practical.

The target audience for this lesson is someone comfortable with the Linux command line, who has either an NVIDIA GPU with twelve to twenty-four gigabytes of VRAM, or a recent workstation CPU with enough system memory to host the routed experts. The exact split is tunable, which is most of what makes this interesting.

Let's start with the model itself, in one paragraph. Qwen3.6 35B A3B is a mixture-of-experts model from Alibaba's Qwen team. The number thirty-five B is the total parameter count. The A3B suffix means active three B — three billion parameters actually doing work per token. The architecture has two hundred and fifty-six experts per mixture-of-experts layer, of which eight routed experts plus one shared expert fire per forward pass. The practical consequence is that memory cost scales with thirty-five billion parameters, but compute scales closer to a three billion parameter dense model. That is why these models punch far above their compute weight on consumer hardware. The native context is two hundred and sixty-two thousand tokens, extensible further with YaRN scaling. Unsloth publishes GGUF builds at quantisations from one bit, around ten gigabytes, all the way up to BF16 at around seventy gigabytes. For a twenty-four gigabyte VRAM card, the UD-Q4-K-M build, at roughly twenty-two gigabytes, is the usual sweet spot. Even an eight or twelve gigabyte card is reachable if you route the routed-expert FFN weights to the CPU.

Step one is building llama.cpp from source. You can install llama.cpp from Homebrew, from winget, from Docker images, or from the pre-built release tarballs on GitHub. For a Linux server we will build from source. It is the only way to get a binary tuned to your specific CUDA setup, and the project moves fast enough that a checkout from master is often weeks ahead of any package. On Debian or Ubuntu you start by installing git, cmake, build-essential, libcurl development headers, and ccache. For NVIDIA acceleration, you also install the CUDA toolkit from NVIDIA's apt repository, and confirm nvcc minus minus version works.

Then you clone the llama.cpp repository, change into the directory, and run cmake with the CUDA flag enabled, plus the CURL flag enabled. The CUDA flag is what compiles the CUDA kernels. The CURL flag is what lets llama-server resolve shortcuts in the form of "user slash repo colon quant" directly from Hugging Face. Without it you are stuck pre-downloading every GGUF by hand. Then you build, in release mode, with an explicit target list — llama-server, llama-cli, and llama-gguf-split. The explicit target list keeps the build narrow. Without it you compile every example, which doubles the compile time for binaries you will never touch.

If you do not have a GPU, drop the CUDA flag. The CPU build is the same in every other respect. Runtime performance on a thirty-five B A3B model will be in the two to five tokens per second range on a recent workstation, which is fine for chat-shaped workloads but slow for batch jobs.

When the build finishes, the binaries live under the build/bin directory. Put that directory on your PATH, or symlink the two binaries you actually use — llama-server and llama-cli — into /usr/local/bin. Verify with llama-server minus minus version.

Step two is getting the GGUF weights. The model lives at huggingface.co slash unsloth slash Qwen3.6 35B A3B GGUF. There are three reasonable ways to pull it down. Option A: let llama-server do it. If you built with CURL support, you pass the dash h f flag with the repo identifier and the quantisation tag, and the server will resolve the file on first run, cache it under tilde slash dot cache slash llama.cpp, and reuse it afterwards. Option B: use the huggingface-cli download command. More explicit, easier to script, and gives you a known on-disk path. You can swap in any quantisation tag from the repo. The Unsloth UD builds — for Unsloth Dynamic 2.0 — use a calibrated importance matrix to bump load-bearing tensors to higher precision than vanilla Q4_K_M, which materially helps mixture-of-experts models at three-bit and four-bit. Option C: wget or curl the file directly from the Hugging Face LFS URL. Fine for one-off runs, awkward to keep in sync with the repo's revisions.

Pick a quantisation that fits your hardware. UD-IQ2-M at around eleven gigabytes fits a twelve gigabyte card. UD-Q3-K-M at around sixteen gigabytes fits a sixteen gigabyte card. UD-Q4-K-M at around twenty-two gigabytes fits a twenty-four gigabyte card and is the default recommendation. Q8 zero at around thirty-seven gigabytes wants a dual-GPU setup or partial CPU offload. BF16, at around seventy gigabytes, is the reference weights — usually only useful if you have a lot of system RAM and are aiming for maximum quality with CPU offload.

Step three is the runtime flags that matter. llama-server has dozens of flags. For a model like this, six of them are load-bearing and the rest are noise. The model flag, minus m, is the path to the GGUF file — the one non-optional flag. Host and port set the bind address. Default is one twenty-seven dot zero dot zero dot one on port eighty eighty, which is what you want unless you are also putting a reverse proxy in front. Do not bind to zero dot zero dot zero dot zero without an authentication gate.

Context size, minus c or minus minus ctx-size, is the context window in tokens. It is allocated up front in VRAM as a KV cache. A value of zero lets the model pick its native size — two hundred and sixty-two thousand for this model — which will not fit in any sane GPU. Pick a realistic working number. Thirty-two thousand is a good starting point. Doubling the context roughly doubles the KV cache memory.

The N GPU layers flag, dash n g l, is the number of transformer layers to offload to GPU. The conventional value is nine hundred and ninety-nine, which means "all layers", and is correct when you want everything on the GPU. You combine that with the mixture-of-experts offload flags, which we will get to in a moment, when you need to claw back VRAM.

Threads and threads-batch control CPU parallelism for generation and for batch processing respectively. Set threads to your physical core count and threads-batch higher — your logical core count, typically — since batch mode is more parallel-friendly. With full GPU offload this has marginal effect. With CPU-resident experts, it is everything.

Batch size and ubatch size are the logical and physical batch sizes for prompt processing. Larger batches improve prefill throughput at the cost of memory. The defaults of two thousand and forty-eight logical, and five hundred and twelve physical, are fine for most setups.

Parallel, dash n p, is the number of concurrent request slots. Important caveat — the context size is divided across slots. So a context size of thirty-two thousand with parallel of two gives each request a sixteen thousand token window. Default is minus one, which is auto.

The jinja flag turns on the model's embedded chat template, which is what gives you correct system, user, and assistant turn formatting, as well as tool-calling support. Leave it on for chat models. Turn it off only if you have a strict reason.

The api-key flag requires this token on every request. Without it your endpoint is wide open to anyone who can reach the port. With it, OpenAI clients pointed at your URL with this string as their OPENAI_API_KEY environment variable will just work.

Step four is the mixture-of-experts specific flags. This is the part of the lesson that pays the rent. A naive "minus n g l nine ninety-nine" command — meaning "put everything on the GPU" — for a twenty-two gigabyte quantisation on a twenty-four gigabyte card, leaves no room for the KV cache. The trick for mixture-of-experts models is that the routed expert weights are touched only when their expert is selected for a given token. They are the largest tensors in the model and the least-frequently used. If you push them to CPU, and keep attention plus the shared expert on the GPU, you get most of the speed of a fully-resident model for a fraction of the VRAM.

Two flags do this. The first is dash c m o e, or minus minus cpu-moe, which keeps all mixture-of-experts weights on the CPU. Simplest possible knob. Use it when you have minimal VRAM and a fast CPU. The second is dash n c m o e, or minus minus n-cpu-moe, followed by a number N. That keeps the mixture-of-experts weights of the first N layers on CPU, and lets the remaining layers' experts live on the GPU. This is the dial you turn to fill exactly the VRAM you have — no more and no less. There is no formula. You start at a low value, watch nvidia-smi, and creep upward until you are comfortably under the VRAM ceiling.

For finer-grained control, the override-tensor flag accepts a regex matching tensor names. The canonical "push every routed-expert FFN to CPU" recipe is a single override of "exps equals CPU". That one regex catches all the expert FFN weights — the bulky, rarely-touched part — and leaves everything else, including attention and the shared expert, on the GPU. On a twenty-four gigabyte card you can usually run a full sixty-four thousand token context this way.

A quick note on sampling defaults. Qwen3 publishes recommended sampler settings, and they matter more than people expect. For the thinking-mode general case, the recommendation is temperature one point zero, top-p zero point nine five, top-k twenty, and presence penalty one point five. For instruct-style chat, it is temperature zero point seven, top-p zero point eight, and top-k twenty. The server accepts these as CLI flags, or as per-request overrides in the chat completions body.

Step five is verifying the endpoint by hand, before we automate anything. With the server running, the obvious smoke test is a GET request to /v1/models, with your API key in the Authorization header as a bearer token. You should see a single model object whose id matches the GGUF filename, or whatever you passed with the alias flag. If you get an empty list, the server is still loading. If you get a 401, your api-key flag and your Authorization header disagree.

Then a real chat completion. Send a POST to /v1/chat/completions with a JSON body containing a model field, a messages array with a system message and a user message, and a temperature. If that returns a sensible answer, your endpoint is live and OpenAI-shaped. Pointing the Python OpenAI SDK at http colon slash slash one twenty-seven dot zero dot zero dot one colon eighty eighty slash v1, with any non-empty API key, works without further changes.

Step six is wrapping it in a systemd service. Running llama-server in a terminal is fine to confirm the model works. For day-to-day use you want it managed by systemd. Starts on boot. Restarts on crash. Logs to the journal. Runs as a non-privileged user.

First, create a dedicated system user — call it "llama" — with no login shell and a dedicated home under /var/lib/llama. Create the directories the service will need — /srv/models for the GGUFs and /var/log/llama for whatever logs you keep outside the journal — and chown them to the llama user. If you have an NVIDIA GPU, the llama user needs to be able to talk to the device nodes under /dev/nvidia star. On most installs the default permissions on those nodes already allow this. If not, add the user to the video group.

Second, drop an environment file. Putting parameters in a separate EnvironmentFile keeps the unit clean and makes tuning a one-line edit instead of a unit-file rewrite. Save a file at /etc/llama-server.env containing the model path, host, port, context size, gpu layers, n-cpu-moe value, threads, and the API key. Lock it down with mode six hundred, owned by root colon llama, so that only root can write and only the llama group can read.

Third, write the unit file at /etc/systemd/system/llama-server.service. The Unit section says After equals network-online.target and Wants equals network-online.target. That matters more than you'd think — the dash h f shortcut hits Hugging Face, and on first boot you need the network to actually be up rather than just configured. If you pre-downloaded the model, this is less critical, but it costs nothing. The Service section says Type equals simple, User equals llama, Group equals llama, EnvironmentFile points at the env file you just created, and ExecStart invokes llama-server with the environment variables substituted as flags. Then a Restart equals on-failure with a RestartSec of ten seconds, and — this is important — a TimeoutStartSec of six hundred seconds. Loading a twenty-two gigabyte GGUF into VRAM is not instant. Without an extended timeout, systemd will declare the unit failed before the model finishes loading, especially on a cold page cache. Ten minutes is generous. Reduce once you know your actual startup time.

The sandboxing block is standard systemd hygiene. NoNewPrivileges yes blocks setuid escalations from inside the service. ProtectSystem strict makes the filesystem read-only except for explicitly listed ReadWritePaths — in our case /var/lib/llama and /var/log/llama. ProtectHome yes hides every home directory other than the service user's. PrivateTmp yes gives the service its own ephemeral /tmp. ProtectKernelTunables, ProtectKernelModules, ProtectControlGroups, RestrictNamespaces, RestrictSUIDSGID, and LockPersonality round things out. These are not security theatre. They meaningfully reduce blast radius if the service is ever compromised, and they cost nothing on a service that just reads model files and serves HTTP. Finally, LimitNOFILE of sixty-five thousand five hundred and thirty-six raises the open-file limit, which the server can briefly hit with many concurrent slots. The Install section says WantedBy equals multi-user.target, which is what causes systemd to enable the service on boot.

Fourth, you reload systemd and enable the service. systemctl daemon-reload picks up the new unit file. systemctl enable minus minus now llama-server enables it for boot and starts it immediately — the minus minus now flag is the shorthand for "enable plus start". Check status with systemctl status, and tail the journal with journalctl minus f u llama-server. The first journalctl line should be llama-server printing its build info, followed by GGUF metadata, then layer-load progress. When you see "HTTP server listening, hostname one twenty-seven dot zero dot zero dot one, port eighty eighty", the endpoint is live.

To change the context size, or the VRAM layout, you edit /etc/llama-server.env and run systemctl restart llama-server. The unit file itself rarely needs to change once it works.

Let me close with what we deliberately skipped. Reverse proxy and TLS — if you are exposing this beyond localhost, put nginx or Caddy in front of port eighty eighty with a real certificate. Do not bind llama-server directly to a public address. GPU drivers — this lesson assumes a working CUDA stack. Installing the driver and matching toolkit is its own topic. Multi-GPU layouts — with two or more GPUs you can split layers across devices with the tensor-split flag, and assign experts per-device with override-tensor. The same principles apply, but the regex tuning gets fiddly. Speculative decoding — recent llama.cpp supports a small draft model accelerating a larger main model. Public benchmarks on Qwen3.6 35B A3B with an Ampere-class GPU suggest no net speedup on this specific mixture-of-experts model, so it is not worth the complexity here. And llama-swap — if you want to serve multiple models from the same port and swap them on demand, llama-swap sits in front of multiple llama-server instances and routes requests. Once you have one model running stably as a service, swapping it out is a small extension of the same systemd pattern.

What you have at this point is a reproducible, version-controlled local inference endpoint. Identical API surface to OpenAI. Predictable startup behaviour. Sensible sandboxing. And a single environment file to tune. From here it is just a question of what you point at it. Thank you for listening.
