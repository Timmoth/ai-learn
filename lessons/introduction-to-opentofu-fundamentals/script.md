Welcome. In this lesson, we are going to build a clear mental model of OpenTofu. OpenTofu is an open source infrastructure as code tool. You describe your cloud or on-premises infrastructure in plain text files, and OpenTofu figures out how to create, update, and tear it down. It is governed by the Linux Foundation, written in the Go programming language, and licensed under the Mozilla Public License version 2. By the end of this lesson, you will understand what OpenTofu is, where it came from, what the main pieces of a configuration look like, what files live on disk, and the four commands that drive the whole tool.

Let's start with where OpenTofu came from. OpenTofu began life as a fork of HashiCorp's Terraform. In August of 2023, HashiCorp re-licensed Terraform under something called the Business Source License, which restricts commercial use by anyone offering a competing product. In response, a coalition of companies, including Gruntwork, Spacelift, Harness, Env0, and Scalr, forked the last open source version of Terraform and donated the project to the Linux Foundation. The result is OpenTofu, which keeps the original open source spirit and is governed by a multi-vendor technical steering committee, so that no single company controls its direction.

The practical consequences for you, as a beginner, are these. OpenTofu uses the same configuration language as Terraform, called HashiCorp Configuration Language, or HCL for short. It uses the same state file format. It uses the same provider plugin system. The command line tool is called tofu instead of terraform, and for most existing projects, migrating is as simple as replacing the binary. OpenTofu has started to add its own features, such as native state encryption, early variable evaluation, and ephemeral values, but the fundamentals you learn here apply identically to Terraform. For the rest of this lesson, just treat OpenTofu as the tool. Anything you learn transfers cleanly back to Terraform if you ever need it.

Now let's talk about infrastructure as code itself, in about a minute. Traditionally, setting up a cloud server meant clicking through a web console or running ad-hoc shell commands. You would create a virtual machine, attach a disk, open a port. That works for one server, but it does not scale, it is not reproducible, and there is no record of who changed what. Infrastructure as code flips this around. You write a file that describes what you want. For example, you might say: I want an AWS EC2 instance of this size, in this subnet, with this security group. The tool then figures out the API calls needed to make that happen.

Two important ideas come along for free. First, the approach is declarative. You describe the destination, not every footstep. Re-running the same configuration is safe. Second, the approach is idempotent. Applying the configuration to infrastructure that is already in the desired state changes nothing. OpenTofu sits in the same family as Terraform, Pulumi, AWS CloudFormation, and Crossplane. Its niche is being cloud-agnostic. One configuration language, one workflow, that works against thousands of different providers.

Next, the three concepts that make up almost every OpenTofu configuration you will ever write: providers, resources, and data sources. A provider is a plugin that teaches OpenTofu how to talk to a specific API. So there is an AWS provider, an Azure provider, a Google Cloud provider, a Kubernetes provider, a GitHub provider, a Cloudflare provider, a Datadog provider, and thousands of others. The Public OpenTofu Registry hosts all of them. Without providers, OpenTofu cannot manage any infrastructure at all. The providers are the things that know how to translate "create a virtual machine" into the right HTTP calls. You declare which providers you need in a special block at the top of your configuration, telling OpenTofu where to download the provider from and which versions are acceptable, and you then configure each provider with things like which region to use or which credentials to authenticate with.

A resource is a single object that OpenTofu will create, update, or destroy on your behalf. A virtual machine, a DNS record, an S3 bucket, a Kubernetes deployment. Every resource type is implemented by a provider. When you declare a resource, you give it two labels. The first label is the resource type, for example aws_instance, where the aws prefix tells you which provider implements it. The second label is a local name you choose, which you use to refer to that resource elsewhere in your own configuration, for example to read its identifier or its public IP address.

A data source is the read-only cousin of a resource. It lets OpenTofu look up information about something that already exists, without managing it, and then use that information elsewhere in your configuration. Fetching the latest Amazon Linux image identifier, reading a secret out of Vault, looking up an existing virtual private cloud. Those are all data sources. The mental shorthand here is: resources write, data sources read.

Now let's look at the essential project files. A configuration file in OpenTofu is any file ending in .tf, or .tofu, which OpenTofu prefers over a same-named .tf file and which Terraform ignores. Every such file in the same directory is concatenated together into a single module before evaluation. That means splitting your configuration into multiple files is purely for human readability. It has zero effect on behaviour. By convention, a small project has three files at the root.

The first is main.tf. This holds the core resources, data sources, and provider blocks. It is the "what to build" file. The second is variables.tf. This declares the input variables your configuration accepts. It is the "what's adjustable" file. Variables are how you parameterise a configuration so the same code can deploy to dev, staging, and production with different inputs. Each variable has a type, an optional default value, an optional description, and optional validation rules, such as requiring an instance count to be between one and ten. You supply values on the command line using the dash var flag, through .tfvars files, or through environment variables prefixed with TF_VAR_. Inside the configuration, you reference variables by writing var dot, followed by the variable name.

The third file is outputs.tf. This declares the values your configuration exposes after it runs. Things like the public IP address of a server, a generated database password, or a connection string. Outputs are useful for humans reading the apply output, and for other configurations that consume your state remotely. You can also mark an output as sensitive, which hides its value from the CLI output. There is nothing magical about these three names. OpenTofu would behave identically if you put everything into one big file. The convention exists because human readers expect it.

Now, the part that confuses newcomers most: state files and the .terraform directory. OpenTofu does not just read your configuration and call APIs. It also keeps a state file. When you create a resource, OpenTofu records its real-world identity, for example an AWS instance identifier, into a JSON file called terraform.tfstate in your project directory. The next time you run OpenTofu, it uses the state file to answer the question: does the thing I described already exist, and what is its real-world identifier? Without state, OpenTofu would have no way to map your friendly resource name back to the actual instance it created last time.

Three things to remember about state. First, it is the source of truth for OpenTofu's view of reality. Editing it by hand is strongly discouraged. There is a dedicated tofu state command for any surgery you need to perform. Second, state often contains secrets. Database passwords, private IP addresses, generated tokens, anything OpenTofu touches gets recorded. So treat the state file as sensitive information. Third, for team use, you should store the state remotely. A local state file works fine for one developer, but real teams configure a backend, such as an S3 bucket, Google Cloud Storage, or a dedicated platform, that stores state centrally with locking, so that two people cannot apply changes at the same time. OpenTofu version 1.7 and later also supports native state encryption out of the box.

Sitting next to your state file is the .terraform directory. That is a hidden directory that OpenTofu creates and manages for you when you run the init command. You do not write to it by hand, and you do not commit it to version control. It holds the cached provider plugin binaries that were downloaded from the registry, copies of any external modules your configuration references, a record of which workspace is currently active, and the last known backend configuration, in case it needs to migrate state on the next run.

There is one more file worth knowing about: the dependency lock file, called .terraform.lock.hcl. This sits alongside your .tf files, not inside the hidden .terraform directory. It is automatically created or updated by the init command, and it records the exact provider versions and cryptographic checksums that were selected for your project. You do commit this file to version control. It pins your teammates and your continuous integration system to the same provider builds, and it protects you from someone publishing a tampered provider version. Today, the lock file tracks providers only. Module versions are not yet locked.

Finally, let's talk about the four commands that drive everything: init, plan, apply, and destroy. You run these from your project directory.

The first is tofu init. This initialises a working directory. It is the first thing you run in any new project. It downloads the providers declared in your required providers block, downloads any external modules your configuration references, configures the backend where state lives, and creates or updates the dependency lock file. You re-run init whenever you add a new provider, change a backend, or upgrade dependencies.

The second is tofu plan. This is the preview step. OpenTofu reads your configuration, reads the current state, and queries each provider to see what really exists in the world. It then computes the difference and prints what it would do. What resources would be created, what would be updated, and what would be destroyed. It does not change anything yet. You read the plan, sanity check it, and only then apply. In team workflows, the plan output is typically posted as a comment on a pull request, so other engineers can review it before anything happens for real.

The third is tofu apply. This executes the change. By default, it first computes a plan, prints it, and asks you to type "yes" before doing anything irreversible. Behind the scenes, it calls each provider's API to bring the world into line with your configuration, and it writes the resulting resource identifiers back into the state file. You can also save a plan to a file and apply that exact saved plan later, which is a common pattern in continuous integration pipelines.

The fourth is tofu destroy. This is the opposite of apply. It destroys everything currently tracked in state for the active workspace. It is very useful for tearing down temporary environments, like test infrastructure or short-lived demos, without manually deleting resources in a cloud console. Like apply, destroy shows you a plan first and asks for confirmation before doing anything.

The whole development loop looks like this. You edit your .tf files. You run tofu plan to see what would change. You run tofu apply to actually make the change. Later, when you no longer need the infrastructure, you run tofu destroy to remove it all.

Let's put it all together one more time, because the full mental model is now small enough to fit in a single paragraph. You write .tf files describing resources, and read-only data sources, each of which belongs to a provider plugin. You run tofu init to download those providers into the .terraform directory, and to record their exact versions in the lock file. You run tofu plan to preview the difference between your configuration and reality, and then tofu apply to make it real. OpenTofu records what it created in the state file, so the next run knows what already exists. Reusable building blocks live in modules. Parameters live in variables. Useful return values live in outputs. And when you no longer need the infrastructure, tofu destroy tears it all down.

From here, the natural next step is to install OpenTofu on your machine, write a tiny main.tf file that creates a single local resource, such as a file on disk using the hashicorp/local provider, which needs no cloud account, and then run the full cycle: init, plan, apply, and finally destroy. Once that works, you have everything you need to point OpenTofu at a real cloud. Thanks for listening.
